# Quickstart Validation Guide

これは実装済み機能の検証手順。実機と初見利用者の確認は未完了。
本番DBを検証に使用しない。契約の詳細は[server-actions](contracts/server-actions.md)、
[MIDI判定](contracts/midi-evaluation.md)、[データモデル](data-model.md)を参照。

## 前提とセットアップ

- Node.js 22、npm、専用PostgreSQL検証DB、HTTPSまたはlocalhost、Web MIDI対応ブラウザー。
- GitHub OAuth検証用アプリ、認証用秘密値、MIDI楽器と接続許可。
- 既存.envの値を出力せず、必要変数DATABASE_URL/AUTH_SECRET/AUTH_GITHUB_ID/AUTH_GITHUB_SECRET/IMPORT_PREVIEW_SECRETを設定。
- 運営1人、限定リポジトリ管理者1人、招待編集者2人、非メンバー1人を用意する。
- 運営セットアップ手順でOPERATORを付与し、他ユーザーが自己付与できないことを確認する。

```bash
npm ci
npx prisma generate
npx prisma migrate dev
npm test -- --run
npx tsc --noEmit
npm run lint
npm run build
npm run dev
```

マイグレーションは実装済みの専用DBにだけ適用する。環境起因の生成・build失敗は理由を記録する。
既存fixtureロード画面とsrc/s-core/fixtures/coreを楽譜の確認に使う。
信頼度テストにはテスト専用設定を運営画面で登録する。
例: initial=0、wAdmin=wOutcome=wReview=1、採用+10、却下-2、評価係数1、
評価範囲-1..1、スコア範囲0..100、mergeThreshold=10。これは本番既定値ではない。

## シナリオと期待結果

| Scenario         | 操作                                                         | Expected / spec                                       |
| ---------------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| 保存と表示       | 音高・音価・休符・拍子・調号・テンポを修正し、マージ後再読込 | 値が一致、対象外不変。SC-001                          |
| 同時マージ       | 同じ版から2案を出し、2つの接続で同時にマージ                 | 片方だけ採用、他方競合、履歴消失0。SC-002             |
| 全ユーザー編集   | 基準未満の人が提出しマージを試す                             | 提出成功、マージ拒否。基準と同値は成功。SC-007/008    |
| 招待限定         | 管理者がメンバーへcanMergeを付与して取り消す                 | 付与中は低信頼度でも成功、取り消し後は拒否。SC-007    |
| 設定変更競合     | マージと同時にルール版/権限を変更                            | 直列化された適用根拠を監査、部分成功なし。SC-008      |
| 自己加点         | 自己評価を送信し、権限ある自分の案を自己マージ               | 評価拒否、自己マージ採用加点なし。SC-008              |
| 算出再現         | テスト設定で他者採用+10、却下-2、他者評価+1                  | 9。直接調整と設定新版後の期待値も確認。SC-008         |
| MIDI記録         | 選択機器で正音・誤音・早い/遅い打鍵・連打を演奏              | 入力保持、種類別/小節別分析一致。SC-003               |
| 境界判定         | 合成入力で±30ms/±60ms/±150msと±1µs境界を検証                 | 幅内含む、外は別判定。3回同一。SC-003/006             |
| 和音/タイ/テンポ | 和音欠落・余分な音・タイ継続・途中テンポ変更                 | 契約どおり採点、再生と基準時刻一致。SC-003/006        |
| 満点/無演奏      | 全期待音を最高判定で演奏、別回で打鍵なし                     | 100/0。SC-006                                         |
| 履歴・再送       | 同じclientSessionIdを2回保存し再ログイン                     | 1記録、完了数増加1、自己ベスト条件一致。SC-005        |
| 削除             | 自己ベスト記録を削除して履歴を再表示                         | 生入力/結果がなくなり残る履歴から再集計。SC-005       |
| 機器断/背景化    | 演奏中に抜線またはタブ切替                                   | INTERRUPTED、未入力を通常ミスにしない、正式スコアなし |
| 非対応/拒否      | MIDIアクセスなし・拒否の環境で開く                           | 理由表示、閲覧・編集・過去履歴は利用可能              |
| 権限・情報保護   | 別ユーザーの非公開楽譜/結果/運営Actionを直接呼ぶ             | 読取・変更不可、秘密値を返さない。SC-007              |
| 保存失敗         | 通信を切断して提出・結果保存し再試行                         | 下書き保持、二重計上なし。FR-016                      |
| 楽譜版変更       | 練習後に楽譜を修正し過去結果を開く                           | 古い版と条件を保持、新版で再採点しない。FR-012        |

SC-004はMIDI楽器を持つ初見利用者5人で実施し、4人以上が案内だけで記録と苦手小節特定を完了すること。
認可・同時更新はモックだけで通さず、専用PostgreSQLの2接続による統合検証を行う。
旧Scoreの移行では移行前後の件数/JSONハッシュ/IDを比較し、未管理データが公開されないことを確認する。

## 性能と証跡

plan.mdの暫定環境・入力規模で30回計測しp95、最大メモリ、処理時間を記録。
音声中断、入力遅延補正、cleanupを実機で確認し、ブラウザー版・機器・補正値を記録する。
検証結果にはコミット、テスト対象、成功基準、失敗理由を含める。
テスト結果は実装段階で記録し、設計時点で「動作済み」と扱わない。

## 取り込みの追加検証（SC-009〜013）

[取り込み契約](contracts/score-import.md)の対応表ごとに、既知の音楽内容のfixtureを用意する。
既存src/s-core/fixtures/files/musicxmlとstandard-midi-file、coreを再利用し、raw XMLと保存JSONも追加する。

1. MusicXML4.0 partwise/MXL、SMF0/1 PPQN、Core JSON/Sheet JSONを選び、プレビュー・確認・保存する。
   対応する音楽情報が一致し、閲覧・再生・練習・ゲームの基準が一致することを確認する。
2. 非対応バージョン/構造、MIME違い、壊れたXML/ZIP/MIDI、外部rootfile、展開量超過を入力する。
   理由付き拒否、既存Scoreの変更0件、元データの永続保存0件を確認する。
3. MIDIの同音連打・複数チャンネル・velocity0・途中テンポ・拍子を既知の期待結果で照合する。
4. グリッド半分の前後・同距離・短いduration・和音を含む入力でPRESERVE/QUANTIZEを切り替える。
   元値の復帰、選択単位どおりの丸め、補正警告、音高/トラック保持、保存された設定を確認する。
5. 表示だけのWARNINGは確認保存後に練習可能。音高/時刻のBLOCKINGは保存できても開始・結果保存を拒否する。
   保存/マージによる修正と再検証が通った新版だけで練習・ゲームを開始できることを確認する。
6. 元のbytes/整列前の別コピーがDB・ストレージ・ログ・ブラウザー永続領域へ保存されないことを確認する。
   保存完了・中止・タイムアウト・離脱で一時参照/ワーカー/URLを解放し、元Fileは端末で変更されない。
7. 取り込み結果を既存Scoreに適用する場合、編集案として提出され、通常のマージ条件を迂回しないことを確認する。
8. 不正署名/期限切れ/他ユーザーtoken/警告未確認/結果改ざんを拒否し、再送で二重保存しない。

変換時間・展開量・音符数をplan.mdの条件で測定する。元ファイルを消した後も保存結果の閲覧は可能であり、
別設定で再変換する際には再アップロードが必要であることを案内で確認する。

## analyze指摘の回帰確認

- ヘッダーからnext-authの組み込みログインを完了し、ログアウト後は非公開情報が表示されない。
- 保存前に候補を修正し、新署名・新診断で保存できる。未解決診断の削除や候補の改ざんは拒否する。
- wAdmin=2、重み付きの他要素と上限/下限clampを含むテスト設定で、運営の目標値と調整結果が一致する。

## Git版管理の追加検証

Git CLIと専用の永続テスト保存領域を用意し、アプリのソースGitを利用しない。

1. 新規保存/編集案/マージでGit本文とDB索引のOID・ハッシュを照合し、過去版を閲覧する。
2. 同repoの2案を同基準から採用し、片方だけAPPLIED、他方CONFLICTを確認する。
3. object準備後、DB確定後、main更新後の各停止点を故障注入し、回復workerで再開する。
   履歴/実績/信頼度入力版は一度だけ進み、原本はDB採用OIDと一致する。
4. 運営設定/権限変更と採用の同時実行で、確定時の根拠を確認する。
5. GC後も全採用版・提案・練習参照・準備操作のobjectを読めることを確認する。
6. DB/Gitの組バックアップを専用環境へ復元し、参照するOIDを全照合する。
7. Gitの失敗/欠損/想定外refでは修復が必要と通知し、直接push/任意path取得を許可しない。
8. 元のアップロードファイルがGit object・commit・ログに含まれないことを確認する。

## 今回の依存・回復修正の検証

- 移行前に共通採用/回復の実Git・DB試験を実行し、編集案/信頼度モデルなしの運営移行を完了できること。
- receipt項目記録前を含む全停止点で再起動し、準備refから回収するか再送待ちとなり、推測採用しないこと。
- 書込/worker/GCを停止したgate下でDB/Git/manifestを取得し、同checkpointの全参照OIDを照合すること。
- 意図的に不一致のバックアップ組を作り、復旧時の照合で書込開始を拒否すること。

## 実装後の設定と確認

1. Node.js 22・PostgreSQL・Gitと永続SCORE_GIT_ROOTを設定し、`prisma migrate deploy`・`prisma db seed`を実行する。
   seedは演奏ルール1だけを初期化する。秘密設定とGitHub callbackはdocs/development.mdを参照。
2. GitHubでログインした既存ユーザーに、理由付きのローカルCLIで運営ロールを付与する。
   `node --conditions=react-server --import tsx scripts/grant-operator.ts <user-id> "理由"`。
3. `/admin/trust`で初期値・3入力の重み・採用/却下の変化・レビューの範囲・最小/最大・マージ閾値を確認して有効化する。
   未設定の全ユーザー編集マージは拒否される。投票は実装しない。
4. 公開/招待/管理者限定の閲覧と、招待/全ユーザー編集を選び、対応形式を取り込む。
   5MiB、展開20MiB/100entries、10,000notes、10秒の制限と警告承認を確認する。
5. 練習→履歴→ゲームを同じ楽譜版で確認し、版変更・条件変更・保存失敗再試行・中断・削除を照合する。
6. バックアップ/復元はdocs/development.mdの専用領域手順で実施する。全レプリカは同じPOSIX保存領域のgateに参加させる。
