# Feature Specification: メール＋パスワードのログイン追加

**Feature Branch**: `chore/setup-spec-kit`（現在のブランチ。仕様の識別子は002-email-password-login）

**Created**: 2026-10-14

**Status**: Draft

**Input**: User description: "ログイン方式にメール＋パスワードを追加"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - メールアドレスで登録してログインする (Priority: P1)

GitHubアカウントを使わずに、メールアドレスとパスワードで登録する。
受信した確認メールで本人確認を済ませ、登録した情報でログインできる。

**Why this priority**: GitHubに依存せず、本サービスの楽譜・練習・本人の履歴を利用できる入口を提供する。

**Independent Test**: 未登録のメールで登録し、メール確認前のログイン拒否、確認後のログイン・ログアウト・再ログインを照合する。

**Acceptance Scenarios**:

1. **Given** 未登録の有効なメールアドレス, **When** 条件を満たすパスワードで登録する, **Then** 確認メールの案内を表示し、メール確認まではログインを許可しない。
2. **Given** 有効期限内で未使用の確認リンク, **When** リンクを使用する, **Then** メールの所有を確認した本人がパスワードを最終確定して登録を完了し、メールとパスワードでログインできる。リンク確認だけでは自動ログインしない。
3. **Given** 本人確認済みの登録, **When** 正しいメールとパスワードでログインする, **Then** 同じ利用者として識別し、既存と同じ権限確認と本人用画面を利用できる。
4. **Given** 登録済みメール, **When** 未ログインの別人が同じメールで登録を試みる, **Then** 既存のパスワード・権限・履歴を変更せず、登録の有無が分からない案内を表示する。
5. **Given** 無効な形式のメールまたは条件外のパスワード, **When** 登録する, **Then** 入力の修正箇所を説明し、登録を確定しない。

---

### User Story 2 - パスワードを忘れても利用を再開する (Priority: P1)

パスワードを忘れた利用者は、登録したメール宛ての再設定案内を利用し、新しいパスワードで利用を再開する。
ログイン中の利用者は、現在のパスワードを確認したうえで変更できる。

**Why this priority**: メール認証の導入と同時に、本人がアクセスを回復し、漏えいしたパスワードの利用を止められるようにする。

**Independent Test**: 確認済みのメール利用者について再設定と変更を行い、旧パスワード・旧ログイン状態・使用済み案内が無効になることを確認する。

**Acceptance Scenarios**:

1. **Given** パスワードを設定済みの確認済みメール, **When** 再設定を要求する, **Then** 本人宛てに再設定案内を送り、登録の有無が分からない応答を表示する。
2. **Given** 有効期限内で未使用の再設定案内, **When** 条件を満たす新しいパスワードを確定する, **Then** 旧パスワードと全端末の既存ログイン状態を無効にし、新しいパスワードでログインできる。再設定だけでは自動ログインしない。
3. **Given** 存在しないメール、未確認の登録、またはGitHubだけで利用するアカウント, **When** 再設定を要求する, **Then** 既存アカウントにパスワードを追加せず、存在するメールの場合と同じ公開案内を表示する。
4. **Given** ログイン中のメール利用者, **When** 現在のパスワードを正しく確認して新しいパスワードを設定する, **Then** 変更を確定し、変更した端末を含む既存ログイン状態を無効にする。
5. **Given** 期限切れ・使用済み・改変された案内, **When** 確認または再設定を試みる, **Then** データを変更せず、再要求の方法を表示する。

---

### User Story 3 - GitHubの既存アカウントにパスワードを追加する (Priority: P2)

GitHubで利用中の人は、本人としてログインし直し、現在のアカウントのメールを確認してパスワードを追加する。
楽譜、演奏履歴、信頼度、役割を保持した同じアカウントを、どちらの方式でも利用できる。

**Why this priority**: 既存利用者のデータを分断せず、新しいログイン方式を利用できるようにする。

**Independent Test**: GitHubのみの利用者にパスワードを追加し、両方式の利用者識別・本人履歴・権限が一致し、未ログインの同一メール登録では追加できないことを確認する。

**Acceptance Scenarios**:

1. **Given** GitHubだけで利用する既存アカウント, **When** GitHubで再認証し、現在のメール宛ての確認案内と新しいパスワードを確定する, **Then** 同じ利用者にメールログインを追加し、既存のデータと権限を変更しない。
2. **Given** メールアドレスが一致する別のログイン試行, **When** 同じメールという理由だけでGitHubアカウントを利用しようとする, **Then** 自動でアカウントを統合しない。
3. **Given** 再認証済みでもメール未確認、または認証後に対象メールが変更された, **When** パスワード追加を確定する, **Then** 確定を拒否し、本人確認をやり直す方法を示す。
4. **Given** メールを持たないGitHubアカウント, **When** パスワード追加を開く, **Then** 現在のメールでは追加できない旨を説明し、既存のGitHubログインは継続できる。

---

### Edge Cases

- 確認待ちの登録を繰り返しても第三者は登録を確定できない。メールの所有者は、確認案内から自分のパスワードを最終確定して登録を完了でき、第三者が確認待ち状態で指定したパスワードを知る必要がない。
- 同じ確認・再設定リンクを複数端末で同時に使っても、確定は1回だけとなる。
- メール送信の失敗は確認済み扱いにせず、再送を案内する。完了していない登録や追加をログインに利用できない。
- 新しい案内を発行した場合、同じ目的の古い案内は利用できない。別目的の案内に転用できない。
- メールの大文字・小文字や前後の空白だけが異なる登録は同じアドレスとして扱う。パスワードは空白・大文字・小文字を勝手に変更しない。
- 連続した失敗や確認メールの大量要求は制限し、試行可能になるまでの案内を表示する。期限のないアカウントロックは行わない。
- ログアウト・パスワード変更・再設定後、本人の履歴や非公開本文を表示し続けず、保護された操作も拒否する。
- メンテナンス中は登録、案内の発行・消費、パスワード設定・変更、ログイン状態の作成を確定せず、再試行を案内する。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: GitHubに加えてメール＋パスワードを選べるログイン入口と、メール登録・確認案内の再送・パスワード再設定の入口を提供する。
- **FR-002**: 有効なメールと条件を満たすパスワードで新規登録でき、メールの所有を確認するまでメールログインを許可しない。メール確認時に所有者がパスワードを最終確定し、確認待ちの登録で第三者が指定したパスワードを自動で有効化しない。
- **FR-003**: メールは前後の空白除去と大文字・小文字の統一後に同一性を判断する。既存アドレスの比較にも同じ規則を使い、既存データに衝突がある場合は上書きや自動統合を行わない。
- **FR-004**: パスワードは15〜128文字を受け付け、貼り付けとパスワード管理ツールを利用可能にする。強制的な文字種の混在や定期変更を要求せず、入力した文字列を勝手に切り詰めたり変換したりしない。
- **FR-005**: 確認済みメールと正しいパスワードでログインでき、ログアウト、ログイン期限、権限判定は既存の方式と同じ利用者保護を提供する。
- **FR-006**: ログイン失敗、登録要求、確認メール再送、再設定要求の公開応答から、メールの登録有無や別方式の登録状況を判別できないようにする。形式不正・パスワード条件違反・利用制限は個別に案内できる。
- **FR-007**: メールの確認案内は発行から24時間、再設定案内は30分を有効期限とし、各案内を本人・対象メール・目的に結び付け、改変・期限切れ・使用済み・別目的の案内を拒否する。
- **FR-008**: 同じ目的の案内を新規発行したら古い案内を無効にし、同時利用でも1回だけ確定させる。確認・再設定だけでは自動ログインしない。
- **FR-009**: 確認済みかつパスワード設定済みのメール利用者は、受信した案内で再設定できる。未確認登録やGitHubのみのアカウントの再設定要求で、パスワードを追加・変更しない。
- **FR-010**: パスワード設定済みの利用者は、ログインと現在のパスワードの確認を経てパスワードを変更できる。変更・再設定が成功したら旧パスワードと全端末の既存ログイン状態を無効にし、本人に変更通知を送る。
- **FR-011**: GitHubのみの既存利用者は、15分以内のGitHub再認証と現在のメールの独立した所有確認を経て、同じアカウントにパスワードを追加できる。再認証または対象メールの確認条件が変わったら確定しない。
- **FR-012**: メールの一致だけでログイン方式を連携・アカウントを統合しない。メール方式で新規登録済みの利用者へのGitHub追加は初版の対象外とし、衝突するGitHubログインで既存データを変更しない。
- **FR-013**: パスワードと確認・再設定に使う秘密を平文の永続データ、ログ、画面、利用者取得データに含めない。案内の送信と本人の入力・確認に必要な一時的な取り扱いに限定する。
- **FR-014**: 認証方式の追加だけで、管理者・運営の役割、信頼度、楽譜の権限、演奏履歴を付与・変更しない。新規メール利用者は通常利用者として登録する。
- **FR-015**: ログイン失敗とメール送信要求をメール対象・接続元の両方で制限する。未登録の対象も同じ制限で扱い、複数のサービス実行環境や再送でも制限を迂回できない。
- **FR-016**: メール送信失敗・認証失敗・案内の無効化は、秘密情報を含まない利用者向け案内を返す。公開する配信不能の案内も対象メールの登録状態によらず一致させる。変更の確定後に通知送信だけ失敗しても、成功したパスワード変更を取り消したり二重実行したりしない。
- **FR-017**: ログアウトや既存ログイン状態の無効化後は、本人データの画面表示を終了し、保護された操作を拒否する。
- **FR-018**: 既存のメンテナンス停止に認証方式追加の書き込みも参加させ、停止中の要求を後から無断で確定しない。

### Key Entities _(include if feature involves data)_

- **利用者**: 既存の識別子、役割、信頼度、楽譜と演奏履歴の所有者。ログイン方式が複数でも同じ利用者を維持する。
- **メール認証情報**: 利用者に結び付いたメール、所有確認の状態、パスワード設定の有無、秘密を公開しない照合情報。
- **確認・再設定案内**: 利用者、対象メール、目的、発行・期限・使用状態。同じ案内で複数の変更を確定できない。
- **本人再認証の証明**: どの利用者がどの方式でいつ再認証したか。期限内のパスワード追加に使い、他の利用者へ転用しない。
- **ログイン状態**: 既存の本人識別と有効期限。パスワード変更・再設定による全端末の無効化対象。
- **利用制限と認証記録**: 失敗・送信要求の集計、有効期限、確定した認証情報変更の記録。パスワードや案内の秘密を含めない。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 正常登録、確認前拒否、確認後ログイン、ログアウトと再ログインの受け入れシナリオすべてが期待結果に一致する。
- **SC-002**: メール登録の操作は、メール配信待ちを除いて入力・確認送信・確認完了の3段階以内で完了できる。
- **SC-003**: 改変・期限切れ・使用済み・別目的・同時使用の確認/再設定案内について、不正な確定が0件、同一案内の重複確定が0件となる。
- **SC-004**: パスワード変更・再設定の全確認シナリオで、旧パスワードと既存の全ログイン状態による保護操作が0件成功となり、新しいパスワードで本人の履歴を再確認できる。
- **SC-005**: 既存GitHub利用者へのパスワード追加の全確認シナリオで、利用者識別・役割・信頼度・楽譜所有・演奏履歴の意図しない変更が0件となる。既存のGitHubログインも成功する。
- **SC-006**: 未登録・登録済み・未確認・GitHubのみのメール対象で、同じ種類の失敗/要求に対する公開文言・遷移・制限の適用が一致する。
- **SC-007**: 初期利用制限の各境界と複数実行環境からの要求について、上限を超えたログイン試行・メール送信が0件となり、制限期間終了後は再試行できる。
- **SC-008**: 秘密の露出、未ログインのパスワード追加、他人の案内の転用、認証方式による権限昇格、メンテナンス中の確定は、全確認シナリオで0件となる。

## Assumptions

- 初版は新規メール登録、メール所有確認、メール＋パスワードのログイン、再設定、ログイン中の変更、既存GitHub利用者へのパスワード追加を含む。
- ログインリンクだけによる認証、メールアドレス変更、登録済みアカウント同士の統合、メール利用者へのGitHub追加、多要素認証、パスキーは対象外。既存GitHubログインは維持する。
- サービス用のメール送信元と配信手段を用意する必要がある。送信サービスの選定や実装方法は計画段階で決める。
- メール確認24時間・再設定30分・GitHub再認証15分・パスワード15〜128文字は、未指定部分に対する初版の仮定である。
- 初期の利用制限は、15分間に同じメール対象へのログイン失敗5回、同じ接続元への失敗20回までとする。以降の試行はその期間が終わるまで拒否する。メール送信要求は目的を合算し、1時間に同じ対象3回・同じ接続元10回までとする。基準は運営設定で変更可能とし、適用する値を検証時に記録する。
- メール全体を大文字・小文字の違いなしで扱い、別名や「+」付きアドレスを勝手に統合しない。既存メールに正規化後の衝突があれば、該当利用者へのメール方式追加を止めて運営による確認対象とする。
- パスワード追加のメール確認は、対象の利用者としてログインしている間に完了する必要がある。GitHubが示すメール情報だけではこの機能の所有確認を完了扱いにしない。
- この仕様は002の追加機能であり、001の楽譜・練習プラットフォームと未実施のT079の完了状態を変更しない。
