## User Scenarios & Testing _(mandatory)_

### User Story 1 - 既存の知識で追加機能を理解する (Priority: P1)

既存プロダクトの保守担当者として、追加された機能の概念、責務、命名が既存の同種の機能と一致していて、既存の知識を使って変更箇所を判断したい。

**Why this priority**: 異なる設計様式を覚える負担と、同じ概念を別々に修正する危険を減らす。

**Independent Test**: 楽譜と演奏の時間変換、および演奏結果の判定について、入力・責務の所有者・公開された操作・結果を保守担当者が追跡できるかレビューする。

**Acceptance Scenarios**:

1. **Given** 既存と追加機能に同じ概念がある、**When** 保守担当者が追加機能を確認する、**Then** 既存の表現と処理を再利用しているか、再利用できない具体的な理由を確認できる。
2. **Given** 楽譜と演奏記録を比較する処理がある、**When** 保守担当者が処理の入口を確認する、**Then** 練習条件、期待する演奏、実際の演奏、評価の役割と処理の流れを説明できる。
3. **Given** 実行環境に依存する処理がある、**When** 保守担当者が音楽の計算処理を確認する、**Then** 入出力、画面操作、保存、権限確認との責任の境界を判断できる。

---

### User Story 2 - 整理後も同じ楽譜と練習記録を使う (Priority: P1)

利用者として、内部の整理後も保存済みの楽譜と練習記録を開き、これまでと同じ条件で演奏・分析・ゲームを利用したい。

**Why this priority**: 保守性の改善によって音楽情報や過去の練習実績が変わることを防ぐ。

**Independent Test**: 整理前の代表的な楽譜・演奏記録を整理後に読み込み、表示、再生、分析、採点、履歴の結果を比較する。

**Acceptance Scenarios**:

1. **Given** テンポ変更、休符、タイ、和音を含む楽譜、**When** 整理後に表示・再生する、**Then** 音高、位置、音価、テンポ、拍子、調号、トラック構成が保持される。
2. **Given** 同じ楽譜の版、演奏記録、練習条件、判定規則、**When** 整理前後で分析・採点する、**Then** 音の対応、時間のずれ、集計値、スコア、コンボが一致する。
3. **Given** 保存済みの完了・中断した練習記録、**When** 履歴を開く、**Then** 記録を失わず参照でき、中断後の未評価部分の扱いも維持される。

---

### User Story 3 - 変更全体の範囲と例外をレビューする (Priority: P2)

レビュー担当者として、今回追加・変更された機能全体について、既存のスタイルに整合させる箇所、既に整合している箇所、理由のある例外を確認したい。

**Why this priority**: 演奏処理だけを直して他の領域に同じ問題を残すことや、無関係な全面改修を防ぐ。

**Independent Test**: 対象一覧から各領域の整合判断、その根拠、確認方法を確認する。

**Acceptance Scenarios**:

1. **Given** 楽譜管理・変換・練習・ゲーム・履歴・信頼度に関する追加変更、**When** 対象一覧をレビューする、**Then** 各領域に既存の参照例、整合判断、対象の責務、互換性の確認方法が記録されている。
2. **Given** 既存の書き方が安全性や正確性の要件を満たさない箇所、**When** 整合方針を決める、**Then** 既存の弱点を再現せず、差異の理由と影響を記録する。

### Edge Cases

- テンポが途中で変わる場合、拍と実時間の対応を維持し、単一テンポへの置き換えで情報を失わない。
- 同時刻の和音、同じ音の連打、余分な入力、音を離さず終了した記録の順序と判定を維持する。
- 空の演奏、途中中断、遅延補正の正負、練習範囲の境界における結果を維持する。
- 不正な入力、権限不足、保存失敗で、拒否や整合性の保証を弱めない。
- 既存の類似実装がない領域は、近い責務の規約と憲章を基準にし、参照例がないことを明記する。
- 書き方が同じでも責務の異なる処理を無理に統合しない。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 対象は楽譜練習プラットフォームで追加・変更された音楽モデル、変換、ブラウザー制御、画面、サーバー処理、関連する検証とする。計画時に対象一覧と既存の参照例を確定する。
- **FR-002**: 各領域の概念、命名、責務の持たせ方、公開された操作、入出力の表現を、同じ領域の既存の設計に合わせる。差異を残す場合は不足する要件と理由を記録する。
- **FR-003**: 同じ意味の音楽概念、単位、変換は既存のものを優先して再利用する。再利用できない場合は、意味や精度の差を示す。
- **FR-004**: 練習条件、期待する演奏、実際の演奏、照合結果、分析・採点の役割と処理の入口を明確にし、呼び出し側から一連の処理を追跡できるようにする。
- **FR-005**: 音楽の計算と、機器への接続、画面操作、保存、認証・権限確認の責務を分け、既存の境界を維持する。
- **FR-006**: 演奏記録の入力順序、音高、強さ、開始・終了イベント、実際の相対時刻を保持する。表示や比較のための時間変換で原本を丸めたり変更したりしない。
- **FR-007**: 保存済みの楽譜・演奏記録・練習履歴を引き続き利用できるようにし、今回の整理で保存形式の変更や利用者による移行操作を必要としない。
- **FR-008**: 同じ楽譜の版、記録、条件、判定規則から得られる照合・分析・採点結果と、完了・中断の扱いを維持する。
- **FR-009**: 外部入力の検証、サーバーでの権限確認、重複送信への対応、失敗時の保存の整合性、終了時のリソース解放を維持する。
- **FR-010**: 対象各領域について変更または維持の根拠を残し、無関係な既存コードの全面改修、新機能追加、判定規則変更を含めない。
- **FR-011**: 各変更の確認方法を定め、変更前後の利用者に見える動作と保存データの意味を比較できるようにする。既知の問題は基準結果とともに記録し、意図しない変更として隠さない。

### Key Entities _(include if feature involves data)_

- **楽譜とその版**: 音楽内容と練習対象を固定するための識別情報。
- **演奏記録**: 実際の入力順序、音高、強さ、相対時刻を保持する原本。
- **練習条件と評価結果**: 対象範囲、テンポ、補正、判定規則と、それに基づく照合・集計・採点。
- **整合対象一覧**: 対象領域、既存の参照例、整合判断、差異の理由、互換性の確認方法を示すレビュー資料。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 計画で確定した対象領域の100%について、既存の参照例または参照例がない理由と、整合判断・確認方法をレビュー担当者が確認できる。
- **SC-002**: 計画で確定した代表事例の100%で、整理前後の音楽情報、演奏記録、照合・分析・採点結果が一致する。
- **SC-003**: 保存済みデータの互換性確認事例の100%で、利用者の移行操作なしに楽譜と練習履歴を参照できる。
- **SC-004**: 既存設計を知る保守担当者が、時間変換と演奏評価の2つの読解課題について、入力・責務の所有者・操作の入口・出力の4項目を関連する資料を使って説明できる。確認結果をレビューに記録する。
- **SC-005**: 計画で確定した正常・不正入力・権限不足・中断・再送の確認事例の100%で、従来の許可・拒否・保存結果を維持する。

## Assumptions

- 本仕様の主な利用者は保守・レビュー担当者であり、サービス利用者には内部整理による操作変更を求めない。
- 機能001の追加変更全体を評価するが、修正は整合上の問題がある箇所に限定する。関数やクラスという形式だけを理由に変更せず、各領域の既存設計を基準に判断する。
- s-coreにおける既存のモデル・単位・変換の扱いを優先する。具体的な型名、配置、構造、必要な例外は計画で決める。
- 楽譜の拍を基準とする意味と、演奏記録の実時間を基準とする意味を維持する。
- [楽譜練習プラットフォーム仕様](../001-score-practice-platform/spec.md)と現行の憲章を互換性の基準にする。
- [メール＋パスワード仕様](../002-email-password-login/spec.md)は独立した機能として維持し、その実装を本仕様に取り込まない。
- 機能001のT079にある実機・初見5人の試用確認は保留を維持し、本仕様の確認で完了したとは扱わない。
- これは仕様作成であり、対象一覧の確定とコード変更は後続の計画・タスク・実装で行う。
