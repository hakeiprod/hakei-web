# Feature Specification: 認証UIのHeroUI統一

**Feature Branch**: `chore/setup-spec-kit`（本仕様でのブランチ作成なし）

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "既存の認証UIをHeroUIに統一する。登録・確認・再設定・パスワード変更・追加画面を対象とし、認証仕様や動作を維持する。"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 統一された画面で登録・確認する (Priority: P1)

初めて利用する人が、サービス内のほかの画面と同じ見た目・操作でメール登録、確認案内の再送、所有確認を進められる。入力条件、処理中、成功、失敗を区別できる。

**Why this priority**: 最初の認証操作で画面ごとの違いに迷わず、登録を完了できることが必要である。

**Independent Test**: 登録画面から確認案内を要求し、確認画面でパスワードを確定する。再送・無効入力・通信失敗も含め、現行と同じ結果になることを確認する。

**Acceptance Scenarios**:

1. **Given** 未ログインの利用者が登録画面を開いている、**When** 有効なメールと条件を満たすパスワードで送信する、**Then** 送信中の状態と現行の共通案内を表示し、確認前に自動ログインしない。
2. **Given** 確認メールを再要求できる状態である、**When** 再送を選ぶ、**Then** 同じ画面の操作体系で再送でき、登録済みかどうかを案内から判別できない。
3. **Given** 有効な登録確認リンクを開いた、**When** 所有者が最終パスワードを入力して明示的に確定する、**Then** 現行と同じ登録結果と通常ログインへの案内を表示する。
4. **Given** 条件外の入力または無効な確認リンクがある、**When** 入力・確定を試みる、**Then** 対象の条件や再要求方法を認識でき、無効な操作を成立させない。

---

### User Story 2 - 同じ操作体系でパスワードを回復・変更する (Priority: P1)

パスワードを忘れた利用者とログイン中の利用者が、登録画面と一貫した入力・送信・結果表示で再設定と変更を進められる。

**Why this priority**: 回復・変更は本人の利用継続に不可欠であり、操作の混乱で手続きを中断させない。

**Independent Test**: 再設定要求から確認リンクでの確定、およびログイン中の現在パスワードによる変更を、それぞれ独立して確認する。

**Acceptance Scenarios**:

1. **Given** 再設定が必要な利用者が要求画面を開いている、**When** メールを送信する、**Then** 処理中と共通の送信案内を表示し、登録状態を明かさない。
2. **Given** 有効な再設定リンクを開いた、**When** 新しいパスワードを明示的に確定する、**Then** 現行と同じ再設定結果となり、自動ログインせず通常ログインへ案内する。
3. **Given** ログイン中のパスワード設定済み利用者である、**When** 正しい現在パスワードと条件内の新しいパスワードで変更する、**Then** 全端末で再ログインが必要であることを伝え、成功後は秘密の入力欄を終了する。
4. **Given** 現在パスワードが不正、利用制限中、または通信不能である、**When** 変更を試みる、**Then** 秘密を含まない現行の案内を表示し、再試行できる状態へ戻る。

---

### User Story 3 - 条件に応じてパスワードを追加する (Priority: P2)

GitHubで利用している人が、本人確認とメール確認の順序を把握しながら、ほかの認証画面と同じ部品・操作でパスワードを追加できる。

**Why this priority**: 条件付きの認証操作でも、利用できる手順と不足条件を一貫して理解できる必要がある。

**Independent Test**: GitHubの利用可否、メールの有無、再認証の成否を切り替え、追加画面と追加確認画面の表示・遷移を確認する。

**Acceptance Scenarios**:

1. **Given** GitHubが有効でパスワード未設定の本人が追加画面を開いている、**When** 本人確認を開始する、**Then** 現行の標準GitHub認証へ進み、成功後に確認メールを要求できる。
2. **Given** 有効な追加確認リンクを本人確認した同じブラウザーで開いている、**When** パスワードを確定する、**Then** 同じUserへ追加し、全端末失効と再ログイン案内を維持する。
3. **Given** GitHubが無効、またはメールが欠落している、**When** 設定画面を開く、**Then** 無効なGitHub操作を表示せず、メール欠落時は既存の説明を表示する。
4. **Given** 本人確認の開始やメール要求が失敗する、**When** 操作結果を受け取る、**Then** 内部エラーを表示せず、結果と再試行方法を認識できる。

---

### User Story 4 - 画面幅や入力方法に左右されず操作する (Priority: P1)

小さな画面、キーボード、支援技術、パスワード管理ツールを使う人が、対象の認証手続きを同じ意味と順序で完了できる。

**Why this priority**: 部品の置換によって、現在利用できる入力方法やアクセシビリティを損なわないためである。

**Independent Test**: 対象の5画面種別を狭い画面と通常の画面で確認し、キーボードのみの操作、読み上げに必要な名前と状態、貼り付け・自動入力を検証する。

**Acceptance Scenarios**:

1. **Given** 幅320pxの画面を使っている、**When** 各手続きを進める、**Then** 入力欄・主要操作・結果案内が横スクロールなしで利用できる。
2. **Given** キーボードだけで操作している、**When** 入力欄から送信・関連リンクへ移動する、**Then** 論理的な順序で到達でき、フォーカス位置を視認できる。
3. **Given** 入力エラーや処理結果が発生する、**When** 支援技術で確認する、**Then** 入力欄の名前・条件・エラーの対応と結果の意味を把握できる。色だけで状態を伝えない。
4. **Given** 貼り付けまたは管理ツールによる自動入力を使う、**When** 現行条件内のパスワードを入力する、**Then** 入力値を勝手に変更・切り詰めせず、現行と同じ判定になる。

### Edge Cases

- 登録・再設定・追加で共有する確認画面は、案内の目的に対応する操作・結果・再要求先を維持する。
- リンクの欠落・改変・期限切れ・消費済み、別目的、別ブラウザー、本人確認後のAccount/メール変更を従来どおり拒否する。
- 確認用の秘密は表示用の部品へ露出させず、画面で入力を受け付ける前にリンクの秘密をアドレス欄から除去する。再読み込み時は現行の再要求案内になる。
- 連打や送信キーの反復で同じ画面から処理中の要求を重複送信しない。画面を離れた後に遅延結果を表示しない。
- 長いエラー文、メールアドレス、入力条件の説明が主要操作を隠さない。
- 境界値の15文字・128文字、多言語や絵文字を含むパスワードも現行と同じ文字数規則で扱う。
- GitHubが未設定・一部設定の場合は、空の選択肢や利用不能な追加操作を増やさない。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: メール登録（再送を含む）、目的別の確認、再設定、パスワード変更、パスワード追加の5画面種別について、入力・主要操作・関連リンク・結果案内の見た目と操作を既存画面に統一する。
- **FR-002**: 入力欄には用途を識別できる名前と必要な条件を表示し、エラーは対象入力と関連付ける。状態の意味を色だけに依存させない。
- **FR-003**: 送信中を識別できる表示と操作制限を維持し、処理中の重複送信を防ぐ。成功・失敗後は次の操作または再試行方法を示す。
- **FR-004**: メールの正規化、パスワード15〜128文字の現行規則、原文保持、貼り付け・自動入力・送信キーによる操作を維持する。
- **FR-005**: 確認の目的ごとの確定処理・文言・遷移と、GETで確定せず明示操作でのみ確定する動作を維持する。確認だけで自動ログインしない。
- **FR-006**: 確認用の秘密をアドレス欄から除去して一時的に扱う動作を維持する。秘密を表示・保存・ログ出力する経路を追加しない。
- **FR-007**: 未登録・未確認・確認済み・GitHub専用の対象に対する共通案内、利用制限、既存の拒否条件を維持する。既存の日本語案内は原則として再利用する。
- **FR-008**: 変更・再設定・追加の成功後は、現在の端末を含む全端末失効、本人表示の終了、秘密入力の消去、通常ログインへの案内を維持する。
- **FR-009**: GitHubの利用可否と本人・メール・資格情報の状態による表示条件を維持し、利用できない操作を表示しない。GitHubの本人確認は既存の標準認証へ遷移する。
- **FR-010**: 対象画面は幅320pxおよび1280pxで主要手続きを横スクロールなく完了できる。
- **FR-011**: すべての主要操作と関連リンクをキーボードで利用でき、視認可能なフォーカス、入力欄の名前、条件・エラーの関連付け、結果通知を提供する。
- **FR-012**: 認証方式、本人確認条件、権限、利用制限、保存データ、既存の遷移先・操作順序をこの変更で再定義しない。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 対象5画面種別すべてで、入力・主要操作・関連リンク・結果案内の対応をレビューでき、同じ役割の部品に画面ごとの独自表現が残らない。適切な共通部品がない例外は理由を記録する。
- **SC-002**: 登録・確認・再送・再設定・変更・追加の対象受け入れシナリオが100%期待結果と一致し、本人確認の迂回・重複確定・秘密露出が0件である。
- **SC-003**: 各画面種別の主要操作を、幅320px・1280pxの両方で横スクロールなしに完了できる。キーボードだけの操作でも主要入力・操作・リンクへ100%到達できる。
- **SC-004**: 対象入力の名前と条件・エラー、処理結果を支援技術から識別でき、フォーカス不可・名前なしの主要操作が0件である。
- **SC-005**: 登録は配信待ちを除いて現行の3段階以内で完了し、ほかの対象手続きでも利用者が行う必須手順・入力項目が増えない。

## Assumptions

- HeroUIの利用はユーザー指定および憲章v1.2.0原則VIIに基づく既定制約である。適切な既存部品を優先し、具体的な部品・配置・利用方法はplanで決める。新しいデザインシステムや独自の色体系は導入しない。
- 現行の[メール認証仕様](../002-email-password-login/spec.md)とコミット済みの動作を維持する。表示の一貫性に必要な配置・余白・状態表現は調整できる。
- 対象はサービス独自の認証画面とその内部の案内・ナビゲーションである。標準ログイン選択画面、外部GitHub画面、Header、楽譜・演奏など他機能の全面改修は対象外とする。
- 新しい永続データを追加しない。認証基盤・運用worker・依存更新をこの仕様の対象に含めない。
- 既存のテーマと画面構成を基準とし、配色や余白の個別指定はplanで既存利用例を参照して決める。
- 仕様002の実SMTP配送保留・実OAuth未確認・最終受け入れ待ち、および仕様001の実機/初見試用保留を引き継ぐ。このUI変更の自動検証を、それらの実環境確認の代替にしない。
