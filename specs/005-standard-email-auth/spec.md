**Status**: SMTP/Mailpit実装済み、受け入れ確認中。依存評価の残りと実環境検証はtasks.md/validation.mdで追跡する。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 外部登録なしでログインを開発・確認する (Priority: P1)

開発者はDev Containerでアプリと開発用のメール受信先を起動し、ブラウザーで受信メールを確認してログインできる。メール配送サービスのアカウントや実際の宛先を必要としない。

**Why this priority**: 開発時に外部サービスの登録で止まらず、利用者と同じメールリンクの手続きを確認するため。

**Independent Test**: Dev Containerを再構築して起動し、標準ログイン画面でテスト用メールを入力する。ローカルの受信画面でリンクを開き、保護された画面へ進み、ログアウトする。

**Acceptance Scenarios**:

1. **Given** 外部メール配送のアカウントやAPIキーがない、**When** 文書化された開発環境を起動する、**Then** メール入力からローカル受信・リンクによるログインまで完了できる。
2. **Given** 開発用の宛先を入力した、**When** ログインメールを要求する、**Then** 開発用受信画面で確認でき、外部の実メールボックスへ配送されない。
3. **Given** 開発環境を再作成した、**When** 同じ起動手順を使う、**Then** 外部登録や追加の配送プログラムの自作なしで同じ手続きを再現できる。
4. **Given** 開発用受信先が停止している、**When** メールを要求する、**Then** ログイン成功と扱わず、受信先の起動後に再試行できる。

---

### User Story 2 - 本番の配送先を設定して利用する (Priority: P1)

運用者は本番SMTPの接続情報と送信元をサーバー環境に設定して、利用者へログインメールを届ける。開発用の受信先へ誤配送しない。

**Why this priority**: 開発専用のメール捕捉と、実利用者への配送を区別する必要がある。

**Independent Test**: 分離した検証環境で本番相当のSMTP設定に切り替え、許可されたテスト宛先への到着とリンクによるログインを確認する。資格情報の不正時は認証が成立しないことを確認する。

**Acceptance Scenarios**:

1. **Given** 有効な本番用接続情報と送信元を設定した、**When** メールを要求する、**Then** 指定した配送先を使い、ソースコードの変更を必要としない。
2. **Given** 本番の配送設定が不足している、**When** アプリを利用する、**Then** 開発用配送先へ自動で切り替わらず、利用不能なメール入口を有効にしない。
3. **Given** 配送に失敗した、**When** 操作結果を受け取る、**Then** 認証を成立させず、接続文字列・資格情報・ログインリンクを独自の案内やログへ追加しない。

---

### User Story 3 - 既存の利用者・資産を保持してログインする (Priority: P1)

新規利用者はパスワードなしでメールの所有を確認して利用を始める。既存利用者は同じアカウントとして、権限・楽譜所有・信頼度・練習履歴を引き続き利用できる。

**Why this priority**: 配送方式の変更で、認証や既存の音楽データを損なわないため。

**Independent Test**: 新規/既存の利用者でメールリンクからログイン・保護操作・ログアウトを確認し、移行前後のID・権限・所有・履歴を比較する。

**Acceptance Scenarios**:

1. **Given** 未登録のメールでログインを要求した、**When** 有効なリンクを開く、**Then** 所有確認後に初めて利用者として認証される。
2. **Given** 既存の利用者である、**When** 本人のメールリンクからログインする、**Then** 同じ利用者IDで既存の権限・楽譜・履歴を利用できる。
3. **Given** リンクが改変・期限切れ・使用済みである、**When** ログインを試みる、**Then** 新しい認証状態を作らず、再要求できる。
4. **Given** パスワード版から切り替える、**When** 移行する、**Then** 旧認証情報の削除・再ログインの影響を事前に確認でき、メール正規化の衝突は自動統合せず停止する。

---

### User Story 4 - 設定済みのGitHubでもログインする (Priority: P2)

利用者はGitHubの接続設定が完了している場合に、その標準の入口も利用できる。未設定でも開発用メール認証を利用できる。

**Why this priority**: 任意の別方式の準備を、メール認証の前提にしないため。

**Independent Test**: GitHubの未設定・一部設定・両方設定で入口を比較し、有効時だけ既存の標準認証へ進むことを確認する。

**Acceptance Scenarios**:

1. **Given** GitHubが未設定または一部設定、**When** ログイン画面を開く、**Then** GitHubの入口はなく、メール認証だけを利用できる。
2. **Given** GitHubが設定済み、**When** GitHubを選ぶ、**Then** 標準の認証経路を使い、別人のアカウントをメール一致だけで自動連携しない。

### Edge Cases

- Dev Container内から届く受信画面のリンクを、開発者のブラウザーからも開ける。コンテナ内部だけで有効なアドレスを要求しない。
- 開発用SMTPの停止・接続失敗・ポート競合を、手順と失敗結果から切り分けられる。
- 開発メールの受信画面は開発用アクセスに限定し、メールやログインリンクを本番へ公開しない。
- 再起動で開発用受信メールが消えても、再要求して確認できる。開発メールの永続保存は必須としない。
- 本番の設定不足、認証失敗、TLS条件不一致では、開発用配送や平文接続へ暗黙に切り替えない。
- メール送信の成功と受信先への実到着を区別し、自動試験だけで本番配送の成功と扱わない。
- 修正済みのメールライブラリがAuth.jsの宣言上の互換範囲に収まらない場合、単に確認を無効化して採用せず、採用判断を計画段階へ戻す。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: Auth.js標準Nodemailer Providerと既存Prisma Adapter・標準画面・標準DBセッションを使用する。リンク生成・検証、メール本文、Cookie、CSRF、セッション暗号を独自に実装しない。
- **FR-002**: パスワード認証・専用API/画面/worker・独自トークン/失効管理は再導入しない。現行Resend固有の配送設定への依存を置き換える。
- **FR-003**: サービス側には現在の利用者・役割取得とリポジトリ認可だけを残し、セッションを二重管理しない。Git/DBバックアップに必要な既存接続は保持する。
- **FR-004**: 利用者ID・外部アカウント・楽譜所有・権限・信頼度・練習履歴を保持する。メール正規化衝突は停止し、自動統合しない。配送方式の変更で追加のデータ移行を前提にしない。
- **FR-005**: GitHubは接続設定が揃った場合だけ標準Providerを有効にし、危険なメール一致自動連携を有効化しない。
- **FR-006**: 本番SMTPの接続情報・送信元をサーバー環境で設定できる。設定不足ではメール入口を有効にせず、開発用設定へフォールバックしない。認証済みの暗号化SMTPを利用でき、秘密をクライアントや文書へ含めない。
- **FR-007**: 本番のメール要求・配送の乱用制限はホスティングや配送側の既存機能で設定・確認する。標準認証の導入だけで完了とせず、独自の制限エンジンは再導入しない。
- **FR-008**: 公式の最小構成と既存部品を優先し、新しい認証基盤・専用メール配送API・汎用ラッパーを追加しない。今回の変更に楽譜・採点などの全面改修を含めない。
- **FR-009**: Dev Containerで開発用Mailpitを起動・利用でき、外部サービスへの登録・APIキー・SMTP資格情報なしでメールの捕捉とブラウザー確認ができる。開発メールを外部へ中継しない。
- **FR-010**: 開発用の配送先・受信画面と本番設定を明確に分離する。開発環境の起動・受信画面・リンク確認・再起動/再試行、本番設定方法を文書化する。実際のポートや起動方式はplanで定める。
- **FR-011**: 依存導入前に、採用するNodemailer・Auth.js・Mailpitの対象版と実行環境、保守状況、ライセンス、既知の脆弱性、互換性を確認して記録する。利用経路で未対処の脆弱性がある構成や、未検証の互換回避を完成扱いにしない。条件を満たせなければ実装を進めず、代替と判断に必要な情報を示す。

### Key Entities

- **利用者と既存資産**: 同じ利用者IDに結び付くアカウント、役割、楽譜所有、信頼度、練習履歴。配送先の変更で作り直さない。
- **ログイン案内と認証状態**: 有効期限と単回利用を持つ標準のログイン案内、および本人確認後の標準セッション。独自の保存モデルを追加しない。
- **開発用受信メール**: 開発環境で捕捉したテストメール。内容とリンクをブラウザーで確認でき、外部配送や永続保存を必要としない。
- **配送設定**: 開発・本番で分離する接続先と送信元。本番の資格情報はサーバー側のみで扱う。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 外部配送アカウント・APIキー・実メールボックスが0件の開発環境で、起動→メール要求→受信確認→リンク→保護画面→ログアウトの一連の操作が成功する。
- **SC-002**: テストで要求した開発用メールを100%ローカルで確認でき、外部メールボックスへの配送が0件である。
- **SC-003**: 新規/既存利用者のログイン、無効/期限切れ/使用済みリンク、ログアウトの対象シナリオが100%期待どおりとなり、既存ID・権限・所有・履歴の意図しない変化が0件である。
- **SC-004**: 本番相当の設定変更だけで許可されたテスト宛先への配送とログインを確認できる。設定不足・配送失敗時の認証成立と開発先への誤配送は0件である。
- **SC-005**: 文書化された手順で開発環境を再作成しても、外部登録や独自プログラムの追加なしに同じ確認操作を完了できる。
- **SC-006**: 採用する全依存・開発用サービスの互換性と脆弱性判断に未評価が0件であり、未確認の実配送・実外部認証・送信制限を成功扱いにした項目が0件である。

## Assumptions

- Auth.js標準Nodemailer ProviderとMailpitはユーザー指定の制約である。具体的な採用版、依存解決、Dev Containerへの配置・ポート・環境変数名はplanで確認し、specでは固定しない。
- 開発用メールはローカルで捕捉し、本番の実配送は運用者が用意するSMTPを使用する。開発環境の作成に必要なパッケージ/イメージ取得のネットワーク利用は許容し、外部メール配送アカウントの登録は要求しない。
- 本番のSMTP資格情報や既存の秘密値をこの作業で要求・書換えしない。Mailpitの開発用設定を本番設定の既定にしない。
- パスワード認証廃止の方針、[仕様002](../002-email-password-login/spec.md)と[仕様004](../004-heroui-auth-ui/spec.md)を置き換える範囲は維持する。旧認証データ削除・全利用者再ログインを伴う既存移行ファイルは別にレビューし、稼働DBへ自動適用しない。
- plan/tasksはSMTP方式へ更新済み。validationは旧Resend方式の履歴とSMTP方式の結果を区別して保持する。既存のテスト通過や実装完了チェックを、新しいSMTP/Mailpit構成の検証結果として転用しない。
- 既知の互換範囲と脆弱性の問題はplanで評価する。2026-10-18の計画更新では隔離検証済み固定版と最小overrideを限定例外として採用した。公式peer範囲外は残り、本体適用後の検証と本番受け入れは別途必要。本仕様の完成だけで安全性・互換性の確認完了とは扱わない。
- 仕様001の実MIDI/初見試用と、実メール配送・実GitHub OAuth・本番の送信制限の未確認項目は引き継ぐ。
